Technical Code Review

Polaris Operations Base App

Independent technical review of the Microsoft Dynamics 365 Business Central operations extension for Polaris Foods A/S — 563 AL objects across 9 modules, reviewed module-by-module against AL best practices.

App v27.0.0.10 BC Cloud · Platform 25 Runtime 16 Object IDs 50000–50149 Overall grade: C

Executive Summary

The Polaris Operations Base App is a business-critical extension that runs the company's production reporting, warehouse movements and external integrations (WMS, EDI, the OEE platform, label printing and cloud file exchange). It is in active production use and compiles cleanly with zero errors, and its module structure is sound.

However, this review found material risks that are invisible in day-to-day operation: a cluster of correctness defects that silently write production data into the wrong tables, no automated test safety net across 563 objects, and uneven error handling in the integrations that can quietly stall warehouse jobs or leave files unprocessed.

None of these are emergencies, but together they raise the cost and risk of every future change. We recommend a focused remediation of roughly two to three sprints — fixing the data-integrity defects first, hardening the integrations, and standing up a baseline test suite — before the next wave of feature work.

Code Quality & Correctness Adequate · 68

The application compiles with 0 errors and the static analyzer reports roughly 23 warnings. The headline concern is not the warning count but a small cluster of silent correctness defects in the Operation module, plus a pervasive pattern of unguarded record reads.

Most significant findings

P1 · correctness  PASTA operation objects read and write NEST tables. The Operation module keeps parallel object sets for the NEST and PASTA production lines. Several PASTA objects were clearly cloned from the NEST versions without updating their table references, so PASTA logic persists water- and finished-goods registrations into the NEST tables. No error is raised — data simply lands in the wrong place, producing incorrect reporting and polluted NEST data.

// OperationReportPasta.Table.al — OnValidate("Production Order")
var
    FinishedGood: Record "Finished Good NEST";   // should be "Finished Good Pasta" (50041)
    WaterAcc:     Record "Water Accounting NEST"; // should be "Water Accounting Pasta" (50043)

P1 · pattern  Unguarded Get() / FindFirst() before field access. The single most widespread issue: setup and master records are fetched without checking the return value, then fields are read from a possibly empty record. The failure is silent — blank values flow downstream, or a validation fails later with a cryptic message far from the cause.

P2/P3 · UX  Localization & help gaps. Hardcoded Danish user-facing strings instead of translatable Labels, errors raised without record context, missing ToolTip/Caption on many custom fields, and a handful of spelling mistakes in captions.

Test Coverage At-risk · 38

The review found no automated AL test codeunits (Subtype = Test) anywhere in the 563-object codebase. Every change — including the correctness fixes above — is therefore validated only by manual testing, and there is no regression safety net protecting the integrations or posting routines.

For a codebase this business-critical, this is the largest single risk to change velocity: each release carries avoidable uncertainty, and refactoring the PASTA/NEST defects is harder to do safely without tests to lean on.

Architecture & Maintainability Adequate · 71

The codebase is cleanly split into nine modules with consistent file/object naming for the most part, and the review confirmed the app is genuinely modular rather than monolithic. The maintainability drag comes from configuration and debt, not from structure.

Key themes

  • Hardcoded configuration. Journal templates, batch names and posting groups are selected via hardcoded strings (several already marked // TODO: Hardcoded values). If a setup is renamed, the flow fails silently. These belong in a dedicated Polaris Setup table.
  • Number series via FindLast() + 1. Several keys are allocated by incrementing the last record rather than a No. Series — not concurrency-safe and bypasses standard logic.
  • Dead / obsolete code still active. Objects marked "delete this" are still running; layout reports broadly suppress warnings behind a refactor TODO; legacy DotNet ("Ping Pong DLL") references cannot run in the cloud.
  • Naming & performance drift. The Snail tables alternate names for the same concept; a few CalcFields calls sit inside loops.

Recommendation: Introduce a Polaris Setup table and move all hardcoded templates/groups into it with TestField validation — this also clears a large share of the // TODO debt. Switch key allocation to No. Series, and make one explicit decision on each obsolete object (remove with an upgrade step, or drop the TODO).

Security & Upgrade-readiness Adequate · 64

The app targets a current platform (BC Cloud, Platform 25 / Runtime 16) and ships permission sets, so it is broadly upgrade-ready. The risks here are integration robustness, background-execution safety and data governance.

Integration robustness

  • exit inside a file loop skips the commit and cloud file deletion — one unknown file leaves all remaining files unprocessed and undeleted.
  • CODEUNIT.Run of a posting batch without checking the result, yet the batch is deleted regardless — a failed posting still deletes data.
  • Unhandled HTTP status in the OEE-platform call: an HTTP 500 is treated as success.
  • Fragile EDI parsing writes into a fixed array with no bounds check, and collected import errors are never surfaced.

Background & data governance

  • Message() / Confirm() without GuiAllowed() in code that can run from the Job Queue — fails or hangs in the background. (One module already does this correctly and is a good template.)
  • Missing DataClassification on a number of fields, despite the table header setting it — worth completing for GDPR clarity.
Show technical detail

ManualWhseImportFunction.Codeunit.al:44-50 (use continue per file; reserve exit for a critical stop). ProcessWMSImport.Codeunit.al:587 (check posting result before cleanup at :591). OeeProdOrderService.Codeunit.al:36-38 (parse Response.HttpStatusCode()). Background dialogs in ReleaseSalesDocSubscribers.Codeunit.al:29. Missing per-field DataClassification on RawMaterialPackNEST.Table.al (fields 8–88).

Recommendation: Standardize integration error handling — wrap external calls in try patterns with explicit status checks, set documents to a "Failed" state on error (enabling retry), and replace background Message/Confirm with GuiAllowed() guards or persisted logging. Complete per-field DataClassification in a single pass.

Prioritized Recommendations

Suggested order — highest correctness/stability impact first, with quick wins bundled in:

  1. Fix the Operation PASTA/NEST defects (P1). Highest data-integrity risk and isolated changes. Verify the whole PASTA folder against its NEST counterpart. Impact: stops silent data corruption.
  2. Harden the integrations (P1). exit→continue in cloud import, check posting Run results, validate HTTP status, add EDI bounds checks. Impact: prevents data loss and stalled Job Queue runs.
  3. Remove the unguarded Get() pattern (P1). Enable AA0175 and route reads through shared setup-getter helpers. Impact: turns silent failures into clear, actionable errors.
  4. Stand up a baseline test suite (P1). Operation reporting + WMS posting first, wired into AL-Go CI. Impact: a regression safety net for everything above.
  5. Move hardcoded config to a Setup table (P2). Clears a large share of the // TODO debt at the same time. Impact: fewer silent setup-rename failures.
  6. Background safety, number series, governance (P2). GuiAllowed() guards, No. Series allocation, per-field DataClassification. Impact: Job Queue-safe, concurrency-safe, GDPR-clear.
  7. Cleanup: localization, dead code, performance (P3). Translatable labels, remove obsolete objects, hoist CalcFields out of loops. Impact: lower long-term maintenance cost.
